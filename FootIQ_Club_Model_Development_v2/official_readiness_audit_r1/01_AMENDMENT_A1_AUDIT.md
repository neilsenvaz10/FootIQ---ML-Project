# 01 Audit of amendment A1 (final proposed text) against the frozen protocol r1

Compared: `shadow_integration_r1/docs/04_REVISED_PROTOCOL_AMENDMENT_A1_FINAL_PROPOSED.md` vs `matched_v1_prospective_r1/09_PROSPECTIVE_EVALUATION_PROTOCOL.md` (hash in `PREREGISTRATION_r1.json`, unchanged). Neither file was edited. Verdict per check: OK / OK-with-edit / **MUST FIX** (affects the validity of the prospective evaluation if left as is).

| # | Check | Finding | Verdict |
|---|---|---|---|
| 1 | Accepted sources, Bundesliga-only scope | A1.1 is explicit (S1 all, S2 `bl1`/2026, S3 confirmation-only). **Conflict with r1's gates:** r1 needs >= 25 competitions and a 12-month hard end; a Bundesliga-only run (~306 matches/season) can never reach the first checkpoint, the 12-month clock would expire first, and r1's bootstrap clusters (competition x month) would be only ~8 clusters. A1 does not say whether Bundesliga batches count toward the pre-registered sample. | **MUST FIX** (AA-1) |
| 2 | Canonical record when S1 and S2 agree | A1.2 takes score and date from S1 and kickoff/result type from S2. Gaps: no mechanism ingests **newer S1 snapshots** into a verified universe or de-duplicates them against S2 rows (logger v2 reads only the frozen universe + S2; a refreshed universe changes the universe hash the logger verifies); the "date" is a local calendar date while S2's is UTC, and a one-day difference is tolerated yet changes `days_rest`/ordering. | **MUST FIX** (AA-2, AA-3) |
| 3 | Conflicting scores and identities | A1.3 covers score, completed-vs-not, date > 1 day, duplicates. **Identity problems are not conflicts**, and a completed record that is rejected for any reason (unresolved/ambiguous team, no explicit 90-minute type, kickoff after retrieval) silently leaves a played match out of the feature state while the clubs' fixtures stay eligible (reproduced: adversarial tests 6/6b). Retraction (completed → not completed in a later snapshot) is called a conflict but not detected (test 7). | **MUST FIX** (AA-4) |
| 4 | Explicit 90-minute requirement | A1.4(1)(2)(4) is clear and implemented (`After90Minutes` only; Unknown/ET/penalty excluded). Ambiguity: A1.4(3) needs a second snapshot >= 24 h later and the first >= 48 h after kickoff, but no deadline for confirmation and no polling duty are stated; unconfirmed fixtures have no defined status. | OK-with-edit (AA-6) |
| 5 | Retrieval-time and historical-feature leakage | A1.5.1–.4 are sound and tested (strict as-of, kickoff < retrieval, canary, prefix invariance). Gap: A1.5.3 admits S1 results but the S1 path for new snapshots is undefined (see 2); scope validation of a snapshot (league/season/dates > cutoff) is absent (test 5: a 2025 snapshot adds 18 results). | **MUST FIX** (AA-2, AA-5) |
| 6 | Kickoff snapshot freshness | A1.6.1 (<= 24 h) is clear. Ambiguity: it does not say the **results** snapshot must be the same fresh one (it is, because one payload carries both); A1.6.3 ("sources disagree by > 30 min → earlier") is unusable because only S2 states UTC (S1 has local time, no zone). | OK-with-edit (AA-7) |
| 7 | Prediction-sealing deadlines | A1.7.1 clear (kickoff − 60 min, no backdating). **Conflicts with r1 eligibility (f)** (date 00:00 UTC − 14 h − 60 min) and A1.8 refers to (a)–(g) of r1 without saying A1.7 supersedes (f) for fixtures with a UTC kickoff. No rule that only the **first** sealed prediction per fixture/model counts (re-sealing is possible: test 1). No clock rule (system clock vs server time). | **MUST FIX** (AA-8, AA-9, AA-10) |

Gaps: "rescheduled later" stays eligible although the 14-day staleness test was done for the **original** date; "removed from newest snapshot" is triggered by a single snapshot (a partial payload could void fixtures); OpenLigaDB has no explicit postponed/cancelled flag, so these are inferences. | **MUST FIX** (AA-11) |
| 9 | Fixture identity changes | A1.6.4 makes them ineligible; tested. Need "present in two consecutive snapshots" to avoid transient edits. | OK-with-edit |
| 10 | Late-arriving or missing results | **Late-arriving history results** (a match played before the fixture but entered in the source after sealing): no rule. **Missing own result:** ineligible after 7 days *permanently* — a result entered on day 8 is lost, which can bias the sample if delays correlate with anything. | **MUST FIX** (AA-12, AA-13) |
| 11 | Attribution and provenance | A1.9 is adequate (ODbL line, S1 commit/file, S3 revision, no contact data). Logger records carry snapshot ids/hashes/state hash; **not recorded:** hashes of feature code outside the logger file and of the original-v1 preprocessing/Elo parameters (tests 8). | OK-with-edit (AA-14) |
| 12 | Metrics and statistical gates preserved | A1 states they are unchanged; textually true, but see 1: with Bundesliga only, the **bootstrap clustering, the 25-competition gate and the 12-month end are not applicable as written**, so "unchanged" is not enough. | **MUST FIX** (AA-1) |

## Required edits (redline suggestions; the A1 file itself was not changed)
* **AA-1 Stage statement.** "Official batches limited to `bl1`/2026 form Stage 1 of the pre-registered sample and count toward it. Model-comparison statistics are produced only when the r1 gates are met. Until a second competition is added by amendment, only descriptive interim reports (coverage, eligibility, calibration of nothing, data quality) are produced. The 12-month hard end runs from the first batch in which >= 25 competitions are eligible, or is extended by amendment. In a single-league stage the bootstrap cluster is the matchday." (and acknowledge in the owner's decision that r1's gates will not be met by the Bundesliga alone).
* **AA-2 S1 updates.** "New S1 snapshots enter only through the ingestion run (`e3`), producing a merged universe with its own sha256, recorded in each record; de-duplication by (competition, season, home, away); agreement is checked before either record is used. Until then the pinned S1 universe is the only S1 input."
* **AA-3 Date used for ordering/features:** the S1 date if S1 holds the match, otherwise the date of the S2 UTC kickoff; a difference of one day is logged; > 1 day is a conflict.
* **AA-4 Incomplete-history event.** "Any completed in-scope record that cannot enter the feature state for any reason (unresolved/ambiguous identity, no explicit 90-minute type, kickoff not before retrieval, scope violation, retraction) is an incomplete-history event: the clubs concerned (the whole competition if they cannot be identified) are not primary-eligible until it is resolved."
* **AA-5 Scope validation.** "A snapshot is accepted only if every record has leagueShortcut `bl1`, leagueSeason 2026 and a match date after 2026-09-20."
* **AA-6 Label confirmation.** "A fixture's label is evaluated only if confirmed by the analysis checkpoint; unconfirmed fixtures are counted by reason. Operators must poll at least 48 h and again at least 72 h after the last kickoff of each matchday."
* **AA-7** Replace A1.6.3 by: "if two S2 snapshots give kickoffs differing by more than 30 minutes the earlier applies"; add: "the results snapshot used is the same fresh snapshot that supplies the kickoff."
* **AA-8** "A1.7 supersedes condition (f) of r1 for fixtures with a source-stated UTC kickoff."
* **AA-9** "Per fixture and model only the first sealed official prediction is evaluated; later seals are logged as superseded and not evaluated."
* **AA-10** "The sealing timestamp is the system clock, checked against the HTTP Date of the newest poll (skew <= 120 s); explicit timestamps are not accepted."
* **AA-11** Rescheduled later: "the 14-day staleness rule is re-checked against the new date using the snapshot at sealing; a fixture failing it becomes ineligible." Removal requires absence from two consecutive snapshots. State that postponed/cancelled are inferred.
* **AA-12** Late-arriving history: "flag `late_arriving_history_result`, keep eligible, report a sensitivity analysis excluding them."
* **AA-13** Missing result: "pending after 7 days, excluded at the analysis checkpoint if still unconfirmed, counted by reason."
* **AA-14** Provenance: add hashes of all prediction-time artefacts and code dependencies.

## Assessment
A1 is **not suitable for approval as written**. It is close: the content of AA-1…AA-14 is a text revision of roughly a page, and none of it changes the metrics, models or comparators.
