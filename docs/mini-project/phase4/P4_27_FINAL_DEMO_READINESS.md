## 4. Clean startup, restart and shutdown findings
- **Documented startup works from the project directory** (`.\.venv\Scripts\python.exe -X utf8 -m uvicorn main:app --app-dir app --port 8000` and `npm run dev`): tested as a second stack on ports 8001 / 5174 with synchronisation disabled. The backend was ready (`club_prediction_ready: true`) in **about 15-37 s** (cold first start 37 s, later starts 15-18 s), database connectivity and all 67 API checks passed, and the **real UI** worked end to end on the test stack: Home, competition selection, Matches hub, a Champions League prediction (Arsenal v Dortmund: 69.6 / 19.2 / 11.2, labelled "Not validated (indicative only)"), and retrieval of saved simulation run 1 ("View": Bundesliga, 10,000 simulations, seed 1398654699, expected final points and ranges).
- **Normal restart recovery:** three start / stop cycles of the test instance each came back ready and consistent; the production database hash was unchanged by them.
- **The occasional shutdown hang.** Cause not fully proven; evidence: with Python 3.12.14 / uvicorn 0.54 the process sometimes stays at "Shutting down" after Ctrl-C (on the long-running 8000 instance: 2 of the 5 stops of this project, both ended only by closing the terminal tab; idle CPU, no open connection, no database write). In the controlled tests the plain command stopped in about 25 s once (log line "Waiting for background tasks to complete") and in 1-2 s twice; with `--timeout-graceful-shutdown 5` it stopped in about 1 s under load. Every forced stop left the database byte-identical (hash and integrity checked after each).
- **Reliable demo procedure (no new infrastructure):** start the backend with **`--timeout-graceful-shutdown 5`** (a standard uvicorn option that bounds the shutdown); stop it with **one Ctrl-C**; if the prompt is not back after 10 seconds, **close the terminal window** (safe: nothing is writing; SQLite recovers; verified). Never run two backends on port 8000 (closing browser tabs before stopping is a harmless precaution, but I could not prove it matters).
- **Two small frontend issues found while testing the real UI** (not fixed; no code was changed in this phase):
  1. **Season simulator lists past seasons** (reported by you): its Season dropdown reuses the shared `/api/gameweeks` answer, which returns every stored season, 2026-27 first and selected. A finished season is refused ("Not eligible: newest verified result is 165 days old", 0 fixtures to simulate), so nothing wrong is predicted, but the list is confusing. **Fix:** offer only the seasons that still have unplayed fixtures (in practice the current one) in `frontend/src/pages/SeasonSimulator.jsx` (a few lines; the existing season tests need one assertion updated).
  2. **"Predict match" links from the Matches page arrive with the clubs empty in the dev server**: `Predict.jsx` clears the clubs in an effect whose "preselected" guard is consumed by React StrictMode's double effect run (dev only; a production build would not do it). **Fix:** compare the competition with its previous value instead of a one-shot flag. For the demo, pick the clubs in the two drop-downs.
- Minor: `App.jsx` still routes `/worldcup` to the Simulations page (a leftover alias from the removed competition).
